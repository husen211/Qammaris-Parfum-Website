## WAIT-01 — "Kabari saya jika sudah ready" on sold-out products — DONE

Owner 2026-10-26 (card #119, App card husen211/qammaris-reimbursement-management-system#68): a sold-out product page shows "Kabari saya jika sudah ready" instead of "Tanya restock via WhatsApp". The button opens a short form (name + WhatsApp number), and the request goes to the Qammaris App Daftar Tunggu. The "Habis" status dot is now red (`#c62828`) on catalog cards and the product page.

How it works:
- `RestockRequestController` validates the input (name 2–60 characters; number normalized to an Indonesian 628… number; hidden honeypot field; limit 5 per minute and 20 per hour per IP).
- `RestockRequests::record` saves at most one request per product and number within 60 days (the App's waiting period). The `restock_requests` table is also the outbox.
- `waitlist.requested` events go to the App endpoint, signed like the order webhook: same client, same secret, the waitlist path. Delivery runs on the job and on `qammaris:restock-requests:deliver` every minute, with the order-webhook retry schedule and a 24 h give-up.
- App answers: 200 is accepted; 400/422 fail without retry; 401/503/5xx/timeout are retried. `--retry-failed` requeues requests that gave up.
- Once the App accepts a request, the Website clears the name, number and body and keeps only a keyed hash for the repeat check.
- The App contract was agreed between the agents on 2026-10-26. The App files the entry as "Dicatat lewat Website", adds the customer to Pelanggan, and sends a push without the number. An entry for a product that is already available goes to "Siap dikabari". Staff send the WhatsApp message from the App; the Website sends nothing to the customer.

Status: everything sits behind `QAMMARIS_WAITLIST_ENABLED`, which is off by default; with the flag off, the WhatsApp button stays. Released PR120 (production `5c7083c`, 2026-10-26). The `restock_requests` migration was run with Owner approval from a private copy of the package, before the release switch. End-to-end test with Owner approval: request `01M5VPP56GZKJ4N50W4918J4MN` (Mykonos Black Opera 15 ml, "Uji Website", the Owner's number) got HTTP 200 from the App and the contact data was cleared; the App marks that entry Batal "Uji coba Website". The flag was then turned on in production, and the form shows on Habis products (checked at 390 and 1440).

## OPS-DB-BURST-01 — Pages fail during traffic bursts — DONE

Found 2026-10-25 in the maintenance check (card #99): a 4-way parallel sitemap crawl returned HTTP 500 on 65 of 430 pages with `SQLSTATE[HY000] [2002] Operation not permitted`; the same error hit ~500 product requests on 2026-10-22 (07:47 and 12:48 UTC, sequential product slugs, i.e. a crawler). Measured on production: Hostinger refuses new MySQL connections above ~20 per second (socket and TCP alike); `max_user_connections` 75, `wait_timeout` 20 s, so persistent connections were rejected as an option. Fix: `App\Support\RetryingMySqlConnector` (bound as `db.connector.mysql`) retries only this refusal after 100/200/400/800 ms pauses with up to 50% jitter (worst case ~2.3 s extra), all other connection errors fail as before. Production MySQL probe with the connector (no app change): 4 parallel clients at ~40 connects/s failed 35% without and 4% with retries; an extreme 120-connect burst in ~0.1 s 83% → 8%. Sustained traffic far above ~20 PHP requests/s still fails; full-page caching would be the next step if that becomes real traffic. Released PR100 (production `f242599`, 2026-10-25): the same sitemap crawl returned 430/430 HTTP 200 at 4-way (avg 0.19 s, before 65 errors) and 8-way parallelism (avg 0.37 s, max 1.5 s), with no new `laravel.log` lines.
